# 网页翻译体验迭代（2026-10-21）

当前已确认范围包括普通网页核心体验、同源 SPA 自动续译、按网站自动翻译、目标语言、显示设置和快捷键，以及后续追加的跨刷新译文缓存、重复请求合并、显示与生成配置分离、保守语言过滤。保持 MIT、现有品牌、Native Messaging 架构与两请求并发。PDF、OCR、字幕、iframe/Shadow DOM、Windows 和商店分发不在本轮。

下文按阶段保留历史实现和验收数字；最新追加内容见末尾“跨刷新缓存、显示分离与语言过滤”。历史阶段的状态和样本不等同于当前工作树重新验收。

## 阶段 1：等待、取消、计时

已实现：

- Host 翻译总期限默认 180 秒，从进入共享队列开始；排队过期不会调用模型，执行中过期传播 AbortSignal。
- Native 翻译请求 240 秒超时后向同一 port 发送对应 batch/job 的取消控制消息；该控制消息不创建新的 pending 和超时，也不重连。
- 前台请求等待共享 OPTIONS 预热最多 250 ms；超出后取消探测、等待清理、派发一次模型请求。成功预热仍复用连接。250 ms 不是模型响应时限，也不消除冷 TLS 成本。
- 弹窗可导出有限容量的本地性能记录；记录任务/批次编号、阶段和数值，不记录正文、URL、密钥、token 或 provider 原始错误。

实际运行：`npm run check` 159 项通过、类型检查与构建通过；`npm run test:browser` 通过。本地 mock 首次预览 197 ms、滚动新预览 130 ms。这是本机 Chromium/Native Host/mock 验证，不能用作真实模型速度。

## 阶段 2：多段流式与调度

已实现：屏内短段最多 3 块合批，屏外最多 2 块、总计 1800 字符；长段按 1500 字符拆分，优先让其他可见段落获得请求位置。页面与 Host 保持两请求并发。

ChatGPT Responses 与自定义 Chat Completions 都支持多段流式预览；增量 JSON 状态机处理分片转义和 Unicode，按 ID 返回累计文本，Host 40 ms 合并后发回。完整 JSON、段落 ID 完整性和 provider terminal 都通过后才记完成、写缓存。围栏 JSON 仍允许最终解析，但不产生增量预览；明确不支持 stream 的自定义服务才降级重发。自定义服务 terminal 之后另发的 usage 尾帧不等待。

阶段定向验证：provider/host-core **65 项通过**；第二次整合 `npm run check` **231 项通过**。具体最终浏览器数字见下方总验收。

## 阶段 3：动态正文、SPA 与自动翻译

已实现：documentElement 观察器覆盖初始空正文、动态追加、连续改文、删除和 body 替换。节点身份稳定，原文每次失效产生新版本；共享批次中任何源变更会取消本批，未改的其他段落重新排队。旧版本回调不写 DOM 或缓存。

同源 SPA 自动续译支持 pushState、replaceState、前进与后退。Chromium 实测 sender.url 在 SPA 后可能保留初始地址，所以使用浏览器提供的当前标签页地址，同时保留准确 documentId、origin 和导航序号校验。停止/恢复结束本 document 的自动衔接；BFCache 中明确停止的页面也保留本地停止标记。

按站规则保存在扩展本地存储，首次开启由用户动作申请该 origin 的可选权限并注册持久 content script。新 document/刷新重新检查规则和权限，再创建 job。撤销权限、关闭规则、迟到发布的竞争条件都有回归测试。即使浏览器拒绝移除权限，本地规则仍关闭、任务停止，并显示残留权限说明。

阶段定向验证：page/extract **50 项通过**；真实 Chromium 已验证动态正文、SPA、网站注册与刷新链路。动态发现使用 50 ms 合并后的正文扫描，并非局部 DOM 索引；还需要超大页面的专项性能验证。

## 阶段 4：日常阅读设置

该阶段实现 8 种目标语言、双语/仅译文、Alt+A 翻译和 Alt+R 恢复原文。当时两类设置由 Host 持久化，旧配置默认迁移到简体中文和双语；后续显示分离已将显示方式移至浏览器本地自动保存。仅译文在完整成功后隐藏简单原段，链接、交互或嵌套段落保留双语，设置页明确说明此行为。

设置页已验证默认与日语/仅译文两类状态、1280px 亮色和 390px 暗色、离线状态；通过溢出检查并实际查看截图。后台快捷键处理有单元测试；操作系统键位冲突与真实工具栏权限提示需在日常浏览器验收。

## 计时解释

`atMs` 使用各执行层自身的单调时钟，只能在同一进程/页面内相减。用 jobId/batchId 关联上下游事件；共享请求通过后台 reuse.link 映射 provider 编号，按实际模型组去重，不把不同进程的时钟直接相减。Host 重启和页面刷新会清空各自内存记录。缺失用量代表未知，取消不代表零计费。生产阶段记录和固定短句 DNS/TCP/TLS 诊断互为补充。

## 2026-10-21 GitHub 性能定位与调度修复

真实测量发现两类可独立定位的问题：只预热一条连接时第二个并发模型请求仍进行冷 TLS；同屏先处理文件界面标签，延后了文章内容。原宿主矩形也会让长 LI 中远处的文字被当作屏内，影响取消和预取。

本轮实现：

- 冷连接池并发预热已有的两个请求槽，两个 OPTIONS 共用一个 8 秒期限，保留 250 ms 前台接替、无凭证/无正文、每项 64 KiB 和失败清理。没有提高模型并发或空闲保留时间。
- 当文章显著占据 main 时提升其同屏优先级，所有范围继续保留；当前屏始终优先于屏外文章，不宣称减少全部请求或 token。
- 调度和取消采用连续原文 Range 与本段译文的矩形，排除嵌套子树；保留用户仍可见的流式长译文，原文和译文都远离时才释放请求位置。
- 固定阅读集合记录初屏/滚动首字与完成，连续滚动按合并窗口最终视口取样，计时从首个 scroll 算起。中断、失败、原文失效分别记录。
- 新增 `diagnose:report`：只用同层时钟，缺失 Host/用量时保留 unknown，避免将部分记录报告成全程请求数或费用。

## 停留与切换标签页时继续翻译（2026-10-21）

此前仅当前视口和附近范围进入队列，远处正文保持 pending，用户不滚动就不会继续。现在在当前屏幕和附近完成后，按单批次继续处理其余已加载正文。隐藏标签页允许原有请求完成，后续每次只发一批；返回、滚动和动态发现重新计算屏内优先级，总并发仍最多为 2。没有新增权限或改变 Host 空闲保留时间，也不自动滚动或触发网站加载更多。

取消远处批次的条件收紧为“可见页面存在尚未分配请求的屏内正文”，避免译文撑高和滚动锚定反复取消无竞争的后台工作；仍在阅读的流式译文继续保留。需要新的屏内请求时仍可能取消并重发远处批次，以优先当前屏幕，这个取舍并不保证最少请求或最低用量。visibilitychange 只调整调度，不制造滚动阅读计时。停止、恢复、迟到响应和动态原文版本保护保留；整页完成后 popup 仍允许停止动态监听。
