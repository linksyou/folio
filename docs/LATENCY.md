# 延迟诊断

## 当前结论

历史受控样本中，短句第一次请求的主要可观测瓶颈是冷 TLS 握手，不是本地认证、页面流式转发或 JSON 解析。HostService 受控样本中，冷请求约 6.26 秒出现首字，其中 TLS 约 5.12 秒；同一进程立即复用连接后，首字约 1.20 秒。

当前版本在打开弹窗时预热所选服务。Luna 固定短句实测中，冷准备约 5.50 秒（其中 TLS 约 5.16 秒），完成准备后从模拟点击到首字约 1.69 秒；15 秒后复用约 1.56 秒，没有新 socket。预热没有发送模型请求，模型请求复用了这次准备建立的连接。

准备耗时与点击后等待分开计算：打开弹窗立即点击仍需等待剩余建连时间，从打开弹窗到首字的总时间没有凭空消失。浏览器刚启动、Host 已退出或服务主动关闭连接时都可能重新建连。当前数据不能支持固定的“秒开”承诺。

## 当前连接生命周期

Host 使用 `globalThis.fetch` 配合私有 Undici dispatcher，不改变进程的全局 dispatcher。连接池对每个服务地址最多建立 2 条连接，允许 HTTP/2；HTTP/1.1 空闲连接保留至多 60 秒，HTTP/2 会话使用 60 秒的 PING 间隔。扩展后台在没有待处理请求后保留 Native Messaging port 60 秒；port 关闭后 Host 退出并销毁连接池。

弹窗读取有效配置后触发一次 `connection.prepare`，用同一私有连接池向所选 origin 根路径发不带鉴权、正文的 OPTIONS 请求，不跟随重定向、不调用模型。冷态同时发两项 OPTIONS，为现有两个模型请求槽预热；服务端会看到两次普通网络访问。已有连接或正常请求正在建连时跳过额外探测；状态轮询不触发预热。它不会让本地程序永久常驻。

同源预热合并为一次；点击时若仍在准备，真实请求最多等待 250 ms。预算耗尽后终止探测并等待清理，再正常请求；未被真实请求接替的预热仍有 8 秒上限。单个调用者取消不影响共享准备。两项冷态探测共享一个 8 秒期限；已有至少一条连接时不补探测。ready 只表示至少一条连接可用，部分失败时不保证两条 POST 都复用。冷握手可能因提前点击被重新建立，不能把等待预算当成首字保证。

点击后的本地配置读取与页面脚本注入也改为并行，减少本地准备的串行等待。停止、恢复和导航仍会使尚未完成的开始操作失效。这部分没有单独归因的毫秒级测速，不计入上述 TLS 优化收益。

认证与设置文件锁使用独立 key 的修复随本轮完成，但它解决的是并发保存和释放的正确性。受控样本中的有效 access token 读取只占亚毫秒级，锁冲突不是约 9 秒首字延迟的原因。

## 运行诊断

```bash
# 参数一：样本数 1–5；参数二：样本间隔 0–30000 毫秒
npm run diagnose:latency -- 2 0

# 模拟打开弹窗预热完成，再点击；分别记录准备时间与点击到首字
npm run diagnose:latency -- 2 15000 --prepare

# 对照 Node 默认 fetch 的连接生命周期
npm run diagnose:latency -- 2 6500 --default-fetch
```

诊断固定发送公开短句 `Welcome to your bilingual reading space.`。每个样本都是一次真实 ChatGPT 模型请求，会产生实际 token 用量。它使用当前保存的配置和登录状态，但不会把凭证、请求头、输入正文或模型输出正文写入结果；结果只保留阶段耗时、连接协议、状态、模型、思考档位和用量数字。

计时从 HostService 路径开始，因此不包含浏览器 IPC、Native Host 进程启动、页面正文提取和 DOM 更新。关键时间点包括本地设置与认证、DNS、TCP、TLS、请求发出、响应头、首个响应块、首个文本 delta 和完成事件。`--prepare` 另记录 `preparationStarted/Finished`、`translateClicked`，`firstTextAfterClickMs` 只计算点击后的首字等待；准备时间仍完整保留。

客户端能够把冷 TLS 与连接复用区分开，也能测出从请求发出到响应头和首个 delta 的时间。后半段仍同时包含网络往返、OpenAI 侧排队和模型执行；即使有服务端处理时间头，也不能仅凭这些客户端事件继续分离出纯 GPU 计算时间。

## 2026-10-21：前台等待预算与阶段记录

以上冷/热连接样本保留为历史证据。当前真实请求等待共享预热的预算改为 250 ms：到期终止 OPTIONS，等待其清理后派发一次正常请求，不再被慢探测响应拖到完整 8 秒。单独打开弹窗的预热仍有 8 秒上限。提前点击可能中断尚未完成的握手，因此必须分别测量“准备完成再点击”和“立即点击”；该策略限制探测带来的额外等待，不保证所有情况下握手更快。

翻译总期限默认 180 秒，从 Host 接收批次进入队列开始。扩展的 240 秒兜底超时会发送定向取消。底层请求真正返回/抛错后才释放 Host 并发槽；取消无法证明远端已经停止计费。

弹窗“导出性能记录”导出页面/后台/Host 的有限容量内存记录。`jobId`、`batchId` 用于关联，`atMs` 仅在同一执行层和生命周期内比较。阶段包含准备任务、页面提取、批次发送、排队、认证、请求调用、响应头、首个增量、首次可见 DOM 和视口结算；具体字段以当前记录为准。`request.dispatch` 是调用 fetch 前的时间，之后仍可能包含连接准备、DNS/TCP/TLS 和网络，不能将这一段全部称为模型执行。

模型终止事件的 token 数只记录服务明确返回的字段。自定义 API 的用量可能在 finish_reason 之后才发送，当前为及时结束不会无限等待该尾帧；缺失字段代表未知。此记录不保存正文、URL、凭据或原始错误体，重启 Host 或刷新页面后相应记录会清空。

## GitHub 真实页面与双连接实验（2026-10-21）

页面首字与整屏不是同一指标。`reading.*` 固定记录一次阅读停留的原文范围及版本；初始屏立即采样，滚动在 40 ms 合并窗口结束时取最终视口，仍从首个 scroll 计时，并回放窗口内已经出现的可见进度；初始屏的范围完成或明确失败后结算。继续滚动会中断旧停留，不能将其称为整屏完成。`ui.firstVisible` 是 DOM 中首次出现可见非空译文，不是浏览器实际绘制帧时间。固定屏即使后续因译文撑高移出视口，也仍按原集合统计。

本次基线使用 gpt-6-luna、none，Chrome 中指定 GitHub 文件页、1920×902 视口、强制重译。有效样本 `test-results/github-performance/baseline-clean-final.json`：点击到首字 3437 ms；原始首屏 18 个范围完成 17687.5 ms；向下两屏后 19 个范围中已有 3 个完成，新译文 2527.6 ms 出现，固定集合完成 24620.4 ms。页面共发出 16 批，无远屏取消；导出前 Host 已空闲退出，首屏 7 批的 Host 日志丢失。只确认滚动阶段 9 个模型请求及其 1665 输入、1043 输出 token，不能当作全程用量。

更早的旧计时样本 `legacy-baseline.json` 有完整 15 个模型请求，2823 输入、1756 输出 token，推理/缓存均 0，但没有固定屏和滚动首字指标，不能替代上述缺失数据。`baseline.json` 与 `baseline-first-screen.json` 则出现重复译文且被外部滚动干扰，已排除，不用于比较。

独立固定公开短句实验使用生产 HttpTransport + HostService，先预热再同时发两个模型请求。旧单连接预热中，第一项复用连接，第二项 dispatch→实际发送 4495.0 ms，其中 TLS 4490.4 ms；第二项首个 delta 6192.5 ms。双连接预热后，两项都复用准备阶段的 HTTP/2 连接，dispatch→实际发送分别 0.7/1.8 ms，首个 delta 1243.2/1592.7 ms。优化后准备阶段仍花 5573.6 ms；网络和模型波动存在，不能以一次样本计算稳定收益百分比。

两次连接实验各发送 2 个公开短句请求，各消耗 156 输入、24 输出 token，推理/缓存均 0；合计 4 请求、312 输入、48 输出。文件在 `test-results/performance-investigation/two-connection-probe{,-optimized}.{json,md}`。这项实验不包含浏览器 IPC、DOM 提取与页面渲染。


## 跨刷新缓存与共享请求的测量边界（2026-10-21）

本轮从避免重复生成入手：同一完整页面地址、原文、生成版本和指令版本下，完整译文可跨刷新复用；并发重复文字通过共享 provider 组只生成必要的文本。双语/仅译文切换和相同生成配置保存不再使译文失效，已有目标语言证据的正文直接保留。它们可以减少请求及其等待，但不改变未命中请求的冷 TLS 或模型生成速度；尚未新增真实 ChatGPT 对照，不给出提速比例或真实 token 节省量。

后台 `reuse.link` 将页面 job/batch 映射到 provider job/batch，`reuse.end` 记录成功状态和模型组数。汇总按唯一 provider 组计数，避免共享请求被多个页面批次重复统计。纯缓存零请求必须有成功且零模型组的结束证据，不能因 Host 日志缺失就推断零请求。`cacheOnlyBatches` 与 `sharedProviderBatches` 分别表示纯缓存页面批次和共享模型组；有模型请求但无终态 usage 时，真实用量仍未知。一个共享组服务多个页面时，返回的 token 用量属于整组，报告不猜测分摊；不能把多个页面报告直接相加。

语言过滤单独记录 skipped，保留原文可使阅读集合完成，但不会产生译文首字事件。全页无需翻译时首字指标缺失是正常情况，不填为零。后续真实对照需分别记录强制冷生成、持久缓存命中和部分命中，并保留请求数、取消、整屏完成及服务实际返回用量；三类样本不可混成一次模型速度对比。
